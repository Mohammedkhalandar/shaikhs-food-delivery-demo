The owner explicitly authorized the new public demonstration repository, Pages hosting and All Rights Reserved original code/branding. Follow these gates for authorized initial publication and subsequent manual releases. The original private repository must remain untouched.

1. Review `LICENSING.md`; confirm code/name publication rights and a code licensing choice. Confirm a publicly accessible, fictional-only demo with GitHub infrastructure access logging is acceptable. No database/backend/private tester access is part of this site.
2. Confirm the exact new repository name/owner and public site path. Inspect any existing destination before creating/configuring anything; never overwrite unrelated history. Preserve the original private repository, database and Docker resources. This folder contains no `.git`; initialize only fresh history after approval and use the account's verified GitHub no-reply identity. Never copy private `.git`, environments, old reports or CI artifacts.
3. After final approval, create the new public repository and push reviewed source normally, without force. Confirm the new CI verification workflow succeeds. CI has read-only contents permission and never deploys on push/pull request.
4. In the NEW repository only: Settings → Pages → Build and deployment → Source: GitHub Actions. Confirm HTTPS for the eventual `github.io` site. Configure the `github-pages` environment, required reviewer where available, main-only deployment and suitable protection rules before running deployment. Do not modify the existing private repository's Pages/settings.
5. The deployment workflow is manual only. It requires the exact proposed repository, `main`, and the literal confirmation `PUBLISH_STATIC_DEMO`. Build/test/security/browser/audit gates run before uploading ONLY `dist`. Deploy permissions are restricted to the deployment job; all actions are immutable SHA-pinned. `configure-pages` explicitly has `enablement: false`, so it must not silently create/enable hosting. Do not dispatch it before approval.
6. After the owner-authorized run, verify its actual conclusion and proposed HTTPS URL. Test certificate trust, every static asset, refresh with a query/hash, menu/category/basket, dialog keyboard behavior, all four simulated roles, reset, generic 404 return link, persistent fictional/DEMO labels, and HTML CSP in the actual host browser. No live hosted-site acceptance or physical-device acceptance has been claimed by this precheck.

Pages supports static artifacts and project URLs; it does not provide a custom backend or the `_headers` mechanism. See [official custom workflow requirements](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages) and [project site URLs/data collection](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages). If privacy, arbitrary security response headers, authentication or real operations become requirements, stop and perform a separately approved architecture/security review.
